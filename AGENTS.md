# Solitaire

A free Klondike solitaire game for iOS. No ads, no purchases, no account, no
tracking, no analytics: the whole point is to replace the store apps that have
them. Never add a dependency or feature that sends data anywhere.

## Stack

- Swift 6 language mode with strict concurrency, SwiftUI, iOS 17+.
- `SolitaireKit/` is a Swift package holding the engine. It must stay free of
  UIKit/SwiftUI and of Apple-only frameworks so `swift test` runs on macOS and
  on CI without a simulator. Every public engine type is `Sendable`; game data
  are value types. Decoding a `GameState` checks `isValidPosition` (pile
  counts, each card once, face-up flags, foundations by suit from the ace,
  tableau runs, move counter range) so a corrupt save never reaches the board.
- `Solitaire/` is the app. `GameViewModel` (`@MainActor @Observable`) is what
  the board views talk to; it owns the `Game`, the timer, the drag state and
  persistence through the `GameStore` protocol. The settings sheet is the one
  exception: it binds directly to `GameSettings`.
- The Xcode project is generated by xcodegen from `project.yml`. Edit
  `project.yml`, run `xcodegen generate`, and commit both: CI fails if the
  committed `.xcodeproj` is out of date. Never hand-edit the `.xcodeproj`.

## Conventions

- Engine first: a rule change goes in `SolitaireKit` with a test, then the UI.
- Named constants for every size, ratio, count and duration (`BoardMetrics`,
  `GameState.tableauColumnCount`, …). No magic numbers in views either.
- Files ≤ ~500 lines, functions ≤ ~50 lines; split views into small structs.
- Pile and card identity for tests: piles expose accessibility identifiers
  `stock`, `waste`, `foundation-N`, `tableau-N` with value `"<n> cards"`;
  cards are `card-<rank><suit letter>` (`card-10D`, `card-KS`). Controls:
  `undoButton`, `newGameButton`, `confirmNewGameButton`, `settingsButton`,
  `autoCompleteButton`, `drawModePicker`, `settingsDoneButton`,
  `winNewGameButton`; labels `movesLabel`, `timeLabel`, `winSummary`; the
  `winOverlay` container. The waste, foundations and tableau columns are
  accessibility containers so their card identifiers stay reachable; the
  stock is a single button element and exposes no card identifiers. Keep these stable; UI tests depend on them.
- UI-test launch arguments: `--ui-testing` gives an in-memory store and fresh
  defaults. Only with it, `-seed <UInt64>` fixes the deal (required for a
  reproducible board, otherwise the seed is random) and `-drawMode 1|3` sets
  the draw mode; a normal launch ignores both.
  See `AppEnvironment`. UI tests use seed 42, whose tableau tops are
  2♣ 8♣ Q♣ 5♥ 6♠ 5♣ A♥.
- Tests live in the matching test target, one file per source file
  (`GameViewModel.swift` → `SolitaireTests/GameViewModelTests.swift`). Engine
  tests go in `SolitaireKit/Tests/SolitaireKitTests`. Never inline tests.
- Every PR runs: `swift test` in `SolitaireKit`, the `SolitaireTests` unit
  tests and the `SolitaireUITests` on an iPhone simulator. Run all three
  locally before opening a PR (commands in README.md).
- User-facing text is English for now; keep strings in the views so the
  localisation task can move them into a String Catalog later.

## Workflow

- Each task gets its own worktree and branch, ends in a PR, and is reviewed
  and merged by Eric. Don't commit on `main`.
- Lasting knowledge (design decisions, gotchas, plans) goes in the shared wiki
  under `solitaire/…`, not in a `docs/` directory.
