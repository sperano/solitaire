# Solitaire

A free Klondike solitaire game for iOS. No ads, no purchases, no account, no
tracking, no analytics: the whole point is to replace the store apps that have
them. Never add a dependency or feature that sends data anywhere.

## Stack

- Swift 6 language mode with strict concurrency, SwiftUI, iOS 17+.
- `SolitaireKit/` is a Swift package holding the engine. It must stay free of
  UIKit/SwiftUI and of Apple-only frameworks so `swift test` runs on macOS and
  on CI without a simulator. It holds no text players read: card, suit and
  mode names are in the app (`DisplayNames.swift`) so they can be localised.
  Every public engine type is `Sendable`; game data are value types. Decoding a `GameState` checks `isValidPosition` (pile
  counts, each card once, face-up flags, foundations by suit from the ace,
  tableau runs, move counter range, score in range and recycle count the scoring mode
  allows) so a corrupt save never reaches the board. Scoring lives in the
  engine (`Scoring`, `ScoringMode`): the score is part of `GameState`, so undo
  restores it; only the standard time bonus is added by the view model, since
  the clock lives in the app. `Solver` (depth-first search over
  `GameState.solverCandidates()`, transposition table, node budget, cancellation
  closure) decides whether a deal is winnable; `GameState.seed` is the deal
  number players see (`GameState.dealNumberRange`).
- `Solitaire/` is the app. `GameViewModel` (`@MainActor @Observable`) is what
  the board views talk to; it owns the `Game`, the timer (on an injected
  `GameClock`, paused in the background, while Settings is open and in untimed
  mode), the drag state and
  persistence through the `GameStore` protocol, and reports results to
  `StatisticsModel` (`StatisticsStore` protocol; the counting rules are
  `GameStatistics` in the engine). The settings sheet is the one exception: it
  binds directly to `GameSettings`, shows the statistics screen and gets the
  deal number and a play-this-deal action as plain values. With *Winnable deals
  only*, `newGame()` runs `DealSearch` off the main actor and `isDealing` keeps
  the previous board on show, input off, until the solver finds a deal; a
  fixed seed or a deal number typed in is dealt as it is.
  File-backed stores share `JSONFileStorage`.
- The Xcode project is generated by xcodegen from `project.yml`. Edit
  `project.yml`, run `xcodegen generate`, and commit both: CI fails if the
  committed `.xcodeproj` is out of date. Never hand-edit the `.xcodeproj`.

## Conventions

- Animations stay in the view layer (`Solitaire/Views/Animation`): `GameView`
  compares the board before and after every change (`BoardTransition`) and
  flies the cards that changed pile in `FlightLayer`, from frames worked out
  by `BoardGeometry`; the piles hide those cards (`cardsInFlight`) until they
  land. So a new kind of move needs no animation code. Haptics go through
  `HapticPlayer` from the view model (`SilentHaptics` in tests).

- Layout: `BoardMetrics(boardSize:)` sizes the cards from the board's width
  and, when that is the tighter limit (landscape, a short Stage Manager
  window), from its height, with `tableauCardHeights` card heights kept for
  the tableau; `GameView` centres the board. iPhone supports portrait and
  landscape, iPad every orientation plus Split View and Stage Manager
  (`UIRequiresFullScreen` is off in `project.yml`). Keyboard shortcuts live
  in `GameCommands` (scene commands, so the iPad's ⌘ overlay lists them):
  ⌘Z, ⌘N and space, all inert while Settings is open. The New Game
  confirmation is `GameViewModel.requestNewGame()` / `isConfirmingNewGame`, shared
  by the button and ⌘N.
- Engine first: a rule change goes in `SolitaireKit` with a test, then the UI.
- Named constants for every size, ratio, count and duration (`BoardMetrics`,
  `GameState.tableauColumnCount`, …). No magic numbers in views either.
- Files ≤ ~500 lines, functions ≤ ~50 lines; split views into small structs.
  `make lint` (SwiftFormat in check mode, then SwiftLint in strict mode: every
  warning fails, as on CI) enforces these limits, a 120-column width, trailing
  commas in multi-line collections and the rules in `.swiftlint.yml`;
  `make format` rewrites what SwiftFormat can fix. Run `make lint` before a PR.
  The magic-number rule is not enabled: it flags the literals that define a
  named constant, so that rule stays a review rule. A line that is a string
  literal alone may exceed the width; wrap a long sentence with a multi-line
  literal and `\` instead of concatenating. Prefer rewriting a line the
  formatter would wrap awkwardly (name an intermediate value) over a
  `swiftformat:disable` comment.
- Pile and card identity for tests: piles expose accessibility identifiers
  `stock`, `waste`, `foundation-N`, `tableau-N` with value `"<n> cards"`
  (`"1 card"`; UI tests run in English, `cardCount` in `SolitaireUITestCase`);
  cards are `card-<rank><suit letter>` (`card-10D`, `card-KS`). Controls:
  `undoButton`, `newGameButton`, `confirmNewGameButton`, `settingsButton`,
  `autoCompleteButton`, `hintButton` (shown instead of Finish),
  `replayDealButton` (in the new-game dialog), `dealingLabel` (while a
  winnable deal is searched for),
  `drawModePicker`, `scoringModePicker`, `carryVegasBalanceToggle`,
  `winnableDealsOnlyToggle`, `dealNumberLabel` (value: the number),
  `shareDealButton`, `playDealButton`, `confirmPlayDealButton` (the alert's text
  field carries no identifier: alerts drop them; use `app.alerts.textFields`),
  `timerToggle`, `autoFinishToggle`, `hapticsToggle`, `fourColorDeckToggle`, `settingsDoneButton`, `winNewGameButton`,
  `statisticsLink`, `statisticsScopePicker`, `resetStatisticsButton`,
  `confirmResetStatisticsButton`; statistics rows `statsPlayed`, `statsWon`,
  `statsWinRate`, `statsBestTime`, `statsFewestMoves`, `statsCurrentStreak`,
  `statsLongestStreak` with the value as accessibility value (`none` when
  empty); labels
  `movesLabel`, `timeLabel` (absent in untimed mode), `scoreLabel` (absent without scoring),
  `winSummary`, `winScore`, `noHintLabel` (shown when a hint finds no useful
  move); the `winOverlay` container. Cards a hint points at, and the stock
  when the hint is to draw, carry the `isSelected` accessibility trait. The waste, foundations and tableau columns are
  accessibility containers so their card identifiers stay reachable; the
  stock is a single button element and exposes no card identifiers. Keep these stable; UI tests depend on them.
- Accessibility: a card is one element (`accessibilityElement(children:
  .ignore)` in `CardView`) labelled "Seven of hearts, face up" or
  "Face-down card". Pile labels carry the state ("Foundation 2, empty",
  "Column 3, 2 face down", "Waste, seven of hearts on top") while the value
  stays "<n> cards". Face-up cards get a hint and one VoiceOver custom action
  per legal destination (`GameViewModel.destinations`, `moveCards`), so every
  move works without dragging. VoiceOver strings live in
  `BoardAccessibility`. Every animation goes through `Motion.animation` so
  Reduce Motion drops it (card flights, flips, the deal and the win cascade too); card colours come from the `cardStyle`
  environment value (Increase Contrast, four-colour deck). Toolbar buttons
  use `HitTargetButtonStyle` (44 pt). `AccessibilityUITests` runs Xcode's
  accessibility audit on every screen; fix what it finds rather than adding
  to its ignore lists, which hold only documented false positives.
- Keyboard UI tests: after a launch, the first ⌘ keystroke XCUITest
  synthesizes is usually lost (any shortcut, however registered). A test
  that sends ⌘ keys lives in `KeyboardUITests`, whose `setUp` primes ⌘
  with an undo it can see; never retry the keystroke under test.
- UI-test launch arguments: `--ui-testing` gives in-memory game and
  statistics stores and fresh defaults, and keeps a hint up until the next
  move (CI steps can outlast the normal 3 s). Only with it, `-seed <UInt64>` fixes the deal (required for a
  reproducible board, otherwise the seed is random), `-drawMode 1|3` sets
  the draw mode, `-scoringMode 0|1|2` sets none, standard or Vegas
  scoring (standard by default), `-winnableDealsOnly 1` turns the solver
  check on (only meaningful without `-seed`), and `-position <name>` starts from a
  `FixturePosition` board (`completable`, `oneMoveFromCompletable`,
  `deadlocked`) in the chosen modes instead of a deal; a normal launch
  ignores them all. See `AppEnvironment`. Unit tests build the same boards
  through `FixturePosition`, and engine fixtures through `GameState.position`,
  which returns nil for a board legal play cannot reach. UI tests use seed 42, whose tableau tops are
  2♣ 8♣ Q♣ 5♥ 6♠ 5♣ A♥.
- Tests live in the matching test target, one file per source file
  (`GameViewModel.swift` → `SolitaireTests/GameViewModelTests.swift`). Engine
  tests go in `SolitaireKit/Tests/SolitaireKitTests`. Never inline tests.
- `SolitaireSnapshotTests` (swift-snapshot-testing) compares the cards, the
  board, the win panel and Settings with the PNGs in its `__Snapshots__`, in
  light and dark mode, one test file per view. They are recorded on the
  iPhone 17 simulator running iOS 26.5, which CI pins, and skip elsewhere.
  After a deliberate visual change, re-record (README, "Snapshot tests"),
  look at the changed images and commit them with the change.
- Every PR runs: `make lint`, `swift test` in `SolitaireKit`, the `SolitaireTests` unit
  tests, the String Catalog check, the `SolitaireSnapshotTests` and the
  `SolitaireUITests` on an iPhone simulator, then `LayoutUITests` (both
  orientations) and `KeyboardUITests` again on an iPad simulator. Run them all
  locally before opening a PR (commands in README.md; `make check-strings` for
  the catalog).
- The app icon is rendered from `Design/AppIcon.svg` by `swift
  Design/render_icons.swift` (CoreSVG: shapes, transforms and CSS variables
  only, no filters) into the three asset-catalog variants, light on the felt,
  dark and tinted with a clear background; edit the SVG, re-render and commit
  the PNGs. The felt is the `Felt` colour asset: `Theme.felt`, the launch
  screen (`UILaunchScreen` in `project.yml`) and the icon's `--felt` variable
  must stay the same green (`LaunchScreenTests`, `AppIconTests`).
- Languages: English (the source) and French (Canada), in
  `Solitaire/Resources/Localizable.xcstrings`. Never show a `String` the
  catalog doesn't know: SwiftUI literals are looked up by themselves, text
  built in code goes through `String(localized:)` with a whole sentence as the
  key and the variable parts as arguments (never a sentence assembled from
  fragments, though whole sentences may be joined; no `count == 1 ? "card" :
  "cards"`: use the catalog's plural forms), and a
  helper that takes a title takes `LocalizedStringKey`, not `String`. Give a
  `comment:` when the English alone is ambiguous. After adding or changing a
  string, build in Xcode or run `make strings`, then write its French; CI fails
  while the catalog is behind the code, and `LocalizableCatalogTests` while a
  key lacks French, a plural form or an argument the English has. French
  follows Québec usage: *piger*, *pointage*, *boni*, a no-break space before a
  colon and none before `!`, `?` and `;`. A card inside a sentence uses
  `nameInSentence` (French adds the article: "le sept de cœur"). Accessibility
  identifiers and persisted values never change with the language.
- App Store text: `AppStore/metadata/<locale>/<field>.txt` (`en-US`, `fr-CA`;
  fastlane deliver's file names), within the limits `AppStoreMetadataTests`
  checks; copyright and category sit in `AppStore/metadata/` itself. A
  version after the first adds `release_notes.txt` in every language. A change
  to what the app stores or shares updates `PRIVACY.md` and
  `PRIVACY.fr-CA.md`.
- Privacy manifest: `Solitaire/Resources/PrivacyInfo.xcprivacy` declares no
  tracking, no data collected, and a reason for each required-reason API the
  code uses (today only `UserDefaults`, CA92.1). `PrivacyManifestTests` scans
  the app and engine sources for those APIs; using a new one means declaring
  it with Apple's reason code, never silencing the test.
- Releases: `MARKETING_VERSION` in `project.yml` is the version (three
  numbers); pushing the tag `v<version>` on `main` runs `release.yml`, which
  uploads to TestFlight with the run number as the build number. Never set
  `CURRENT_PROJECT_VERSION` by hand. `Scripts/screenshots.sh` takes the store
  screenshots through `ScreenshotUITests` (skipped in normal runs); a new
  screen worth showing gets a shot there.

## Workflow

- Each task gets its own worktree and branch, ends in a PR, and is reviewed
  and merged by Eric. Don't commit on `main`.
- Lasting knowledge (design decisions, gotchas, plans) goes in the shared wiki
  under `solitaire/…`, not in a `docs/` directory.
